# Techno Lot — technolot.ca

Site vitrine Next.js 15 (App Router, Tailwind, Supabase) + dashboard admin + CRM de prospection. Rachat de lots informatiques au Québec. Tout le contenu utilisateur est en français (Québec).

## Commandes

- `npm run dev` — dev sur :3000 (préférer preview_start avec `.claude/launch.json`)
- `npm run build` — build + postbuild `scripts/inline-critical-css.mjs` (ne pas casser ce script, il corrige le LCP)
- `npx tsc --noEmit` + `npm test` (vitest) — à lancer avant tout commit ; `node scripts/verif-garde-admin.mjs` si une route/page/action admin change

## Structure

- `app/(fr)` + `app/(en)/en` — site public bilingue (contenu dans `lib/i18n.ts`, `lib/site.ts`)
- `app/admin/(dashboard)` — dashboard admin : lots, soumissions (`/admin/soumissions`, `lib/admin/soumissions.ts`), calculatrice, CRM (`/admin/crm`, `/admin/crm/[id]`, `clients`, `relances`, `modeles`, `envoi-en-gros`)
- `components/admin/` + `components/admin/crm/` — composants admin
- `lib/admin/` — types/actions/format des lots ; `lib/crm/` — types/actions/email/parse-followup-date du CRM
- CRM → Envoi en gros (`/admin/crm/envoi-en-gros`, `components/admin/crm/EnvoiEnGros.tsx`) : liste collée ou CSV d'Excel analysée par `lib/crm/envoi-en-gros.ts` (pur : parseur, lots de 10, limite du jour, `renderTemplate`), vérification puis envoi lot par lot par `lib/crm/envoi-en-gros-actions.ts` → `envoi-en-gros-serveur.ts` → `sendProspectBatch` (`lib/crm/email.ts`) → `preparerEnvoyeur` (`lib/hostinger/mail.ts`) : les courriels partent de la boîte info@ par la Mail API de Hostinger (POST `/send`, un à la fois, 1 s de pause), qui en range une copie dans « Envoyés » (demande de l'utilisateur, 2026-10-30). Même mise en page et signature que l'envoi manuel, mais sans mention de désabonnement (demande de l'utilisateur, 2026-11-04 : `sansDesabonnement` de `lib/crm/email.ts`, aussi pour le test et l'aperçu ; les adresses désabonnées restent exclues) ; l'API n'accepte ni reply-to, ni copie cachée utile, ni en-tête personnalisé. Premier échec = arrêt : 429 → « débit » (aucun nouvel essai, risque de blocage de l'IP), 413 → « trop lourd », clé refusée → « configuration », pas de réponse ou 5xx → « incertain » (compté et tracé comme envoyé pour ne jamais envoyer deux fois). Pièces jointes (demande de l'utilisateur, 2026-10-30 : photos du lot, liste en PDF ou Excel) : `lib/crm/pieces-jointes.ts` (pur : liste blanche JPG/PNG, PDF, Excel, CSV, Word par octets magiques de `lib/securite/fichiers.ts`, 15 pièces et 7 Mo au total pour rester sous 10 Mo une fois encodées, noms assainis et uniques) ; le navigateur réduit chaque photo à 1600 px et la réencode en JPEG (`components/admin/crm/pieces-jointes-navigateur.ts`, retire la position GPS ; HEIC illisible → refusée), puis envoie un FormData (champ `piece`) avec le test et CHAQUE lot ; `lirePieces` (serveur) revérifie nombre et poids avant de lire, puis le type réel ; mêmes pièces jointes (base64, `contentType` explicite) dans chaque courriel. D'où `serverActions.bodySizeLimit` = 8 Mo dans `next.config.mjs` (toutes les actions sont admin, le middleware refuse /admin/* sans session avant de lire le corps). Bouton « M'envoyer un test » (`envoyerTestEnGros`) : courriel du premier destinataire prêt, à l'admin connecté seulement, objet précédé de « [Test] », par le même chemin (boîte info@), sans écriture dans le CRM et hors limite. Limite (`PLAFOND_QUOTIDIEN` = 100 par jour, heure du Québec, remise à zéro à minuit, `debutJourQuebec`) : seules les traces d'envoi en gros du jour comptent (les courriels envoyés depuis les fiches et les relances, peu nombreux, ne comptent pas) ; rester loin des 3 000 par jour de la boîte protège sa réputation ; le reste de la liste repart le lendemain (arrêt « limite_jour », même liste). 500 destinataires au plus ; case de confirmation + nombre exact ; trace `manual_note` / outcome `envoi_en_gros` (jamais `intro_email_sent` : les relances automatiques l'ignorent), qui exclut au prochain envoi les adresses ayant déjà reçu cet objet ; adresse inconnue → nouveau contact ; étape `new` → `contacted` seulement

## Supabase (projet aznelukkwitvttycwnjb)

- RLS : toutes les tables admin n'acceptent que `(select public.est_admin())` (compte listé dans `public.admins`) → sans session admin, tout est vide (pages locales vides : normal). Schéma `securite` (secret RPC, limites, journal) non exposé à l'API.
- Tables à NE JAMAIS modifier (schéma) : `soumissions`, `lots`, `email_logs`, `sales`. Le CRM peut seulement les lire/lier (`contacts.lot_id → lots.id`).
- Tables CRM modifiables : `companies` (fit_score 1-10, lead_status, next_followup_on, lead_status_changed_at), `contacts` (stage new→…→converted), `outreach_activities`, `email_templates`, `daily_prospect_batches`.
- Tables de l'agent Acheteurs : `acheteurs` (carnet, domaine unique), `recherches_acheteurs` (file et résultats) et `lectures_soumissions` (lecture des pièces jointes), une ligne par soumission, `soumission_id` sans clé étrangère, politiques `(select public.est_admin())` ; l'agent y passe par le rôle service des routes `/api/cron/acheteurs/*`.
- `soumissions` n'a aucune politique de lecture : l'admin la lit via la fonction `admin_soumissions` (security definer, réservée à `est_admin()`). La suppression passe par `admin_supprimer_soumission` (même contrôle ; supprime aussi le lead de pub `ad_leads` du même envoi ; le lot éventuel reste).
- Migrations DDL via l'outil MCP apply_migration, toujours avec le même fichier dans `supabase/migrations/`.

## Sécurité

- Dépôt GitHub PUBLIC : rapports, cartes et inventaire des secrets dans `securite/` (ignoré par Git), jamais ailleurs dans le dépôt ; aucun détail exploitable dans les commits.
- Toute page admin commence par `exigerAdminPage`, toute route par `exigerAdminRoute`, toute action `"use server"` par `adminPourAction` (`lib/securite/garde.ts`) ; `node scripts/verif-garde-admin.mjs` doit passer.
- Validation Zod (`lib/securite/schemas.ts`, `lib/admin/schemas.ts`) au début de chaque entrée ; corps JSON via `lireJson` (taille bornée).
- Erreurs via `reponseErreur` (message générique + réf.) : jamais `error.message` ni texte Supabase/Resend renvoyé au client.
- Limites de débit via `limiter` / `limiterSelon` (`lib/securite/limite.ts`, table `TABLE_LIMITES`) ; événements via `journaliser` (`lib/securite/journal.ts`, jamais de secret ni de mot de passe).
- Blocage de connexion (demande de l'utilisateur, 2026-11-04 : 3 essais, à travers les IP et les VPN ; `app/admin/auth/password/route.ts`) : tout est compté AVANT la vérification, un mauvais nom d'utilisateur compte aussi. Navigateur inconnu : IP (3 / h, 5 / 24 h), puis empreinte des en-têtes (`lib/securite/empreinte.ts`, mêmes nombres), puis total mondial (5 / h, 10 / 24 h), arrêt au premier refus ; refus = `auth.blocage` + courriel d'alerte. Navigateur connu (témoin signé `tl_admin_appareil`, `lib/securite/appareil.ts`, posé après un mot de passe juste) : ses seuls compteurs (3 / 15 min, 10 / 24 h), pour qu'un attaquant ne puisse pas bloquer le vrai admin. Un mot de passe juste efface les compteurs (`effacerLimite`), jamais le total. Code à 6 chiffres : 3 essais / 15 min. Déblocage d'urgence : `delete from securite.limites`.
- Formulaire public (`app/api/soumission/route.ts`, seul point public qui envoie un courriel, pages Soumission et Contact) : IP avant la lecture du corps (3 / 10 min, 5 / 24 h), puis sur les soumissions VALIDES seulement : empreinte (3 / 10 min, 10 / 24 h), courriel et téléphone (3 / 24 h), total (100 / 24 h). Compter l'empreinte avant la validation laisserait un robot griller celle de vrais clients.
- Écritures publiques seulement par les fonctions SQL à secret (`SECURITE_RPC_SECRET`, `lib/securite/rpc.ts`) : aucune politique `anon` nouvelle.
- Toute nouvelle table : RLS activée + politiques `(select public.est_admin())`.
- Jamais de clé secrète en `NEXT_PUBLIC_` ; tout nouveau nom de variable va dans `.env.example` (sans valeur). La clé publishable (`site_prod`, remplacée le 2026-11-04) se traite comme un secret malgré son préfixe : lue côté serveur seulement, jamais dans du code navigateur (aucun `createBrowserClient`) ni dans le dépôt, car elle ouvrirait l'API d'authentification de Supabase hors des limites du site. `tests/securite/http/verifier-build.mjs` et le test des motifs de clé la cherchent. Marche à suivre pour la changer : `securite/SECRETS.md`.
- CSP imposée : `next.config.mjs` (public) et nonce de `middleware.ts` (admin) ; aucun script en ligne sans nonce, aucun `onclick=` en attribut.
- Demander avant d'ajouter un paquet npm (vérifier qu'il existe et est maintenu).

## Conventions

- Toujours répondre à l'utilisateur en français (Québec), même s'il écrit en anglais.

- Thème admin : fond `night-950`, cartes `.glass`, accent vert `#5ECB33` (`.btn-primary`, `.field` dans `app/globals.css`, couleurs dans `tailwind.config.ts`).
- Wording : jamais « paiement avant notre départ » ; dire « paiement rapide et garanti ».
- Git : messages de commit en français.
- Sessions Claude Code dans le nuage (claude.ai/code, branche imposée `claude/...`) : l'utilisateur veut que TOUS les changements aillent sur `dev`. Travailler sur `dev` (`git fetch origin dev && git checkout -B dev origin/dev`) et pousser sur `dev`, pas sur la branche `claude/...`. Vercel déploie une prévisualisation de `dev` automatiquement.
- Workflow multi-ordi : on travaille TOUJOURS sur la branche `dev` (en début de session : `git fetch origin && git checkout dev && git pull`). Commit + push sur `dev` librement après chaque modif terminée (sert à synchroniser les ordinateurs, ne déploie rien). Ne JAMAIS pousser sur `main` sauf si l'utilisateur dit « mets en ligne » : alors `git checkout main && git pull && git merge --ff-only dev && git push origin main`, puis revenir sur `dev`.
- Déploiement : Hostinger depuis GitHub. `.env.production` n'est PAS versionné (ignoré depuis `ba4aeb6`) : l'hébergeur doit fournir toutes les variables, y compris `NEXT_PUBLIC_SUPABASE_URL` et `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (intégrées au build) et `RESEND_API_KEY`. Preview Vercel de `dev` (techno-lot-dev.vercel.app) : variables dans Vercel → Environment Variables, environnement Preview ; sans les deux clés Supabase, le middleware plante sur /admin (500 MIDDLEWARE_INVOCATION_FAILED). `/api/track` n'enregistre rien en local ni sur les Preview (`VERCEL_ENV=preview`).
